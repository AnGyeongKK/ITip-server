# 채팅방·기록과 Python SSE 연동

> 이전 구현 계획이다. 현재 채팅 생성은 [Spring AI 직접 생성 계약](../chat-generation-contract.md)을 따른다. 아래 Python 연동 계획을 새 구현 기준으로 사용하지 않는다.

## 목표

최신 dev `39361fb`에서 #6 채팅방·대화 저장을 구현하고, 그 위에 #7 Python AI HTTP/SSE 연동을 이어 구현한다. 기능별 PR을 분리하고 커밋마다 독립 리뷰를 받는다. #7은 미병합 #6에 의존하면 해당 브랜치를 기반으로 PR을 열고 의존 관계를 명시한다. 병합은 팀 승인 뒤 진행한다.

## 근거와 경계

- Notion CHAT-01~07의 필드·커서·상태·SSE 형식을 유지한다. 로그인·요금·일일 한도는 제외한다.
- Spring MVC/JPA/Java21. chat-app은 별도 실행 앱이며 API·Worker에 의존하지 않는다.
- 외부 AI는 WebClient로 연결한다. GPT 호출·RAG는 Python 담당이다. 실제 서버가 없으면 명시한 내부 계약 초안과 로컬 HTTP/SSE fixture로 검증하고 실제 AI 검증 완료로 표시하지 않는다.
- 사용자 기존 변경 `.agents/rules/api.md`, `.github/pull_request_template.md`는 보존·커밋 제외한다.
- 범위 고정/조건 재평가와 폴더 공유 스키마는 사용자 확인 후 별도 결정 문서에 기록한다. 답변 전에도 앱·공통 HTTP·메시지 저장의 독립 작업은 진행한다.

## 구현 순서

1. Chat 실행 모듈과 실제 중복되는 공통 HTTP 처리. 기존 API 테스트와 새 Chat 응답 테스트로 확인한다.
2. Flyway 채팅방·메시지·출처 저장 및 상태·동시 생성 제약. 삭제된 분석 기록에도 과거 대화가 유지되게 원본 FK와 출처 스냅샷을 구분한다.
3. 방 생성·범위 검증·멱등 처리, 방 목록·상세·삭제를 구현한다. 방 잠금을 생성·삭제에서 공유한다.
4. 메시지 목록·단건·요청 ID 복구, 현재 출처의 삭제 표시를 구현한다. 최신 페이지를 읽되 items는 과거→최근 순이다.
5. #6 전체 빌드·단순화·PR 리뷰·PR·호출 구조 갱신.
6. #7 질문 원자적 접수·한 방 1개 생성, 실패 재요청·기존 요청 중복 검사를 구현한다.
7. Python WebClient·SSE 파싱·출처 검증·부분 저장·최종 커밋 후 done, 끊김·시간 제한·재시작 복구를 구현한다. 외부 대기·스트림 전체를 DB 트랜잭션으로 묶지 않는다.
8. 실제 HTTP 스트림 fixture로 정상·실패·삭제·권한·중복·연결 종료를 검증하고 #7 리뷰·PR·호출 구조를 갱신한다.
9. 코드 읽기 시작점·함수 호출·잠금·트랜잭션·SSE·테스트 실행 안내를 작성한다.

## 확인 기준

- 실제 PostgreSQL에서 소유권·멱등 키·커서 동률·삭제·동시 요청·원본 삭제 후 대화 보존을 확인한다.
- HTTP 오류는 code/message, 성공은 ApiResponse, SSE는 전용 event/data다. meta 이전 실패와 이후 실패를 구분한다.
- 같은 요청은 AI를 다시 호출하지 않는다. 범위 밖 출처는 반환하지 않고 완료 전 저장을 보장한다. EOF만으로 완료 처리하지 않는다.
- 개별 커밋에는 파일별 핵심 로직·확인 결과·Refs를 적는다. 리뷰 지적은 별도 커밋으로 수정한다.
- 실제 Python/GCS/모델 호출과 고정 fixture 테스트의 범위를 구분한다. 비밀 파일·값은 생성·추적·공유하지 않는다.
